# Editorial SEO research for portfolio case studies and technical posts

Researched 2026-10-15. Scope: official Google Search Central guidance, applied to a fullstack developer portfolio and blog. Recommendations about recruiter needs and case-study organization below are editorial applications, not Google ranking requirements.

1. **Write for the actual reader.** Lead case studies with the user problem and what the developer built; lead technical posts with the question the reader can answer afterward. Explain concrete implementation decisions, constraints, and lessons instead of repeating technology names. Google prioritizes useful content, original analysis, firsthand expertise, and a satisfying answer. It has no preferred word count. [People-first content](https://developers.google.com/search/docs/fundamentals/creating-helpful-content)

2. **Make personal contribution and evidence explicit.** Identify the author's role, distinguish individual contributions from team output, and link to available code or demonstrations. Preserve only verified achievements: do not invent user counts, performance gains, revenue, production adoption, leadership, or security guarantees. When evidence is absent, describe implemented behavior and learning. This is an editorial application of Google's emphasis on trust, clear sourcing, author background, and avoiding factual errors. [Content quality and expertise](https://developers.google.com/search/docs/fundamentals/creating-helpful-content)

3. **Give each page a specific, honest title.** Use the project name plus its meaningful purpose, or the technical problem addressed. Keep titles concise and distinct; avoid repeated keyword lists and exaggerated promises. Keep the main visible heading and metadata aligned, with one clearly prominent page title and concise author/site branding. Google can generate a different search title. [Title links](https://developers.google.com/search/docs/appearance/title-link)

4. **Write a unique summary for every page.** A useful excerpt/meta description states the problem, implementation focus, and reader value in natural language. Avoid a generic personal-brand slogan repeated across projects. Google primarily generates snippets from visible content, may use the meta description, and truncates according to the display; a fixed character count is not a Google requirement. [Snippets and descriptions](https://developers.google.com/search/docs/appearance/snippet)

5. **Add contextual internal links.** Connect each important article or project from another relevant page. Cross-link a case study to the technical post explaining its implementation only when useful. Use descriptive anchors such as "JWT authentication implementation" rather than "click here." Render links as real anchors with href values; avoid forced keywords and link quotas. [Internal links and anchor text](https://developers.google.com/search/docs/crawling-indexing/links-crawlable)

6. **Use external links as evidence.** Link project repositories, live demonstrations, and official technical references where they substantiate a statement. Explain the destination in the surrounding sentence. Trusted editorial references do not automatically need nofollow; paid links and user-generated links have separate qualification requirements. [External links](https://developers.google.com/search/docs/crawling-indexing/links-crawlable)

7. **Preserve truthful dates.** Keep the original publication date. Add an actual modification date for a substantive rewrite rather than making an old page appear newly published. Label visible dates clearly, keep structured dates consistent, and distinguish project timelines from page publication dates. Google's date guidance recommends accurate timezones in markup and rejects future publication dates. [Byline dates](https://developers.google.com/search/docs/appearance/publication-dates), [freshness cautions](https://developers.google.com/search/docs/fundamentals/creating-helpful-content)

8. **Make structured data match the page.** For genuine blog articles, applicable Article or BlogPosting properties include headline, author identity URL, representative image, datePublished, and dateModified. Supply applicable facts rather than filling fields speculatively; markup must accurately represent visible content. Validate markup, but do not promise rich results or rankings. Rewriting a project description alone is not a reason to label every project as an article. [Article markup](https://developers.google.com/search/docs/appearance/structured-data/article), [structured-data policies](https://developers.google.com/search/docs/appearance/structured-data/sd-policies)

## Review checklist

Check each rewrite for a clear reader outcome, project-specific evidence, accurate role and stack, defensible claims, distinct title and summary, useful contextual links, and consistent dates. Confirm external destinations and factual technical claims against the supplied project materials before publication. These checks support the recommendations above; they are not a guarantee of indexing, traffic, or hiring outcomes.
